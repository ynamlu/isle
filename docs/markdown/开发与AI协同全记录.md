# 第一部分 · 立项与方案

## 1. 立项

### 1.1 起点

项目最初处于方案探索阶段。用户提出：

> “这个项目可以做成原生安卓 App 吗？并且 AI 只接入 DeepSeek。”

进一步明确：

> “AI 闺蜜、女友、男友、朋友等等，可以自定义角色性格简介，并且有记忆保留。”

随后收敛为：

> “心屿，仅安卓；文档聚焦当前产品。”

### 1.2 100 分钟 MVP

2026-10-15 15:51 开始，约 100 分钟跑通核心闭环：

```text
原生 Android 工程
  → Room 三表
  → DeepSeek SSE 流式
  → 角色 CRUD
  → 端侧 ONNX 记忆
  → Compose 界面
```

### 1.3 当时的四个硬约束

1. 代码必须落在 UI / Domain / Data / 基础设施四层；
2. 使用手写 `AppContainer`，不引入 DI 框架；
3. 状态一律 `StateFlow` 单向输出；
4. 高风险能力先定义接口与失败降级路径。

这四条后来一直保留到当前版本。

---

## 2. 技术选型与关键决策

| 决策 | 原因 |
| --- | --- |
| Kotlin + Compose 原生 | 只做 Android；端侧 ONNX 集成更直接 |
| Room 三表 | 角色 / 消息 / 记忆职责清晰 |
| OpenAI 兼容协议 | 不绑定单一厂商，地址/模型/Key 可切换 |
| 手写 AppContainer | 结构透明，降低 AI 生成隐式依赖 |
| 端侧 bge-small-zh-v1.5 | 隐私、离线、无额外向量服务费用 |
| ABI 拆分 | ONNX 四套原生库会让 APK 膨胀到 185MB |
| 单 Activity + Compose | 页面状态集中，导航简单 |

### 2.1 端侧记忆

- 模型：`bge-small-zh-v1.5` int8，23.9MB；
- 维度：512；
- 池化：CLS + L2 归一化；
- 召回：语义 0.8 + 关键词 0.2 + 重要度 0.1；
- 失败降级：关键词匹配。

### 2.2 为什么保留“记忆”

普通聊天机器人每次从零开始；心屿希望做到：

> “它不是每次重新认识你，而是带着对你的了解出现。”

这是心屿的核心差异化，也是后续迭代一直保留的能力。

## 7. 关键实现

### 7.1 安全路由

```text
SafetyEngine
  → ConversationOrchestrator
      ├─ CRISIS：固定危机话术，退出角色，不调用模型
      ├─ HIGH：安全确认 + 真人资源，不调用模型
      └─ NORMAL：角色/场景/倾听/分析/呼吸
```

设计原则：

- 危机判断不能完全交给 LLM；
- 固定话术包含 12356、120/110、学校心理中心/辅导员；
- 危机内容不写入长期记忆；
- 输出侧再用 `ResponseValidator` 拦截 AI 身份暴露、危险方法、倾听模式给建议。

### 7.2 本地匿名账户

用户要求：

> “登录核验采取本地。”

实现：

- 昵称 + 密码；
- PBKDF2WithHmacSHA256，随机盐，210,000 次迭代；
- 恢复码只显示一次；
- 5 次失败锁定；
- 后台 60 秒应用锁；
- 删除账户清空本地数据；
- 明确不做学籍/实名核验。

### 7.3 记忆管理

- 记忆 Tab 按角色折叠；
- 默认收起；
- 展开只读查看；
- 点「管理」进入单角色记忆管理；
- 支持搜索、编辑、删除、清空；
- 返回/切换 Tab 保持展开状态。

### 7.4 角色与场景

- 去掉恋人；
- 新增老师/家人；
- 首页 8 个场景；
- 场景先选角色，AI 主动开场；
- 场景提示词每次只推进一个小步骤。

## 8. 重构期问题

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| 英文危机表达带空格输入不稳定 | `adb input text` 的分词限制 | SafetyEngine 增加去空格匹配 |
| 测试时微信输入法无法输入 | 输入法服务未及时初始化 | 新增输入框焦点重试，并复测第三方输入法 |
| 记忆折叠返回后丢失 | 状态存在 `remember` | 移入 ViewModel |
| 记忆条目误触跳转 | 整行可点击 | 记忆条目只读，角色组「管理」进入管理页 |
| 聊天页记忆入口过深 | 入口在聊天右上角 | 移除，统一放到记忆 Tab |

# 第四部分 · AI 协同方法

## 14. Prompt 链示例

### 14.1 立项

用户：

> “这个项目可以做成原生安卓 App 吗？并且 AI 只接入 DeepSeek。”

AI：

- 先确认模型 ID 与 baseURL；
- 提示 API Key 反编译风险；
- 给出原生 Android、KMP、跨平台三种路线对比；
- 在用户确认前不改文件。

### 14.2 安全架构

用户：

> “情感分析 Agent 先分析情绪，安全策略路由 Agent 检测高危，人设生成 Agent 输出。”

AI：

- 把“三个 Agent”拆成检测 / 路由 / 生成 / 校验；
- 强调危机判断不能完全交给 LLM；
- 提出本地规则 + 确定性状态机；
- 设计固定危机话术与 12356 资源。

### 14.3 本地账户

用户：

> “登录核验采取本地。”

AI：

- 明确本地无法做邮箱/学籍核验；
- 设计 PBKDF2 + 恢复码 + 应用锁；
- 把账户数据用 Keystore 加密；
- 明确“匿名本地账户”的能力边界。

## 15. 排错闭环

每次问题按四步处理：

```text
1. 保留报错原文
2. 定位根因（依赖 / 配置 / 状态 / 设备）
3. 最小修复
4. 编译 / 单测 / 真机验证
```

例子：

- 记忆折叠返回丢失 → 先复现，确认是 `remember` 状态，再移入 ViewModel；
- 英文危机输入不稳定 → 确认 adb 输入限制，再让 SafetyEngine 支持去空格匹配。

## 16. 用户偏好

- 删除/动设备前先问；
- 密钥只显示掩码；
- 不要 FAB、不要悬浮加号；
- UI 全局统一、液态玻璃、有温度；
- 开发者信息固定三行；
- 文档聚焦当前产品、不强调“比赛版”；
- 源码包不带 `local.properties`；
- 公开分发包不内置上游真实 Key，统一走代理。

## 17. 经验总结

1. **先定边界，再堆功能**：情绪支持不是“角色越多越好”；
2. **安全不能交给模型自由发挥**：确定性路由 + 固定话术；
3. **本地优先**：账号、记忆、向量都尽量留在设备；
4. **状态要放在能活过返回的地方**：ViewModel 而不是 `remember`；
5. **文档与代码同时演进**：页数、版本号、入口、角色都要同步；
6. **真机是最终裁判**：输入法、异常数据、返回栈只有真机能暴露；
7. **客户端藏不住密钥**：能做的不是“永不泄露”，而是让泄露的凭证价值有限、可撤销。

# 第五部分 · 密钥保护与部署

## 18. 从“内置 Key”到 Serverless 代理

### 18.1 问题是怎么暴露的

早期为了“打开就能用”，构建脚本从 `local.properties` 读取模型 Key，写入 `BuildConfig.DEMO_AI_API_KEY`。这在演示阶段很方便，但 APK 一旦公开分发，任何人都可以解包 `classes*.dex`，用 `strings` 找到完整 Key。

问题的本质是：**密钥一旦随 APK 到达客户端，就迟早会被提取**，混淆只能增加难度。

### 18.2 四种方案对比

| 方案 | 真实 Key 是否进 APK | 用户是否要配置 | 适用场景 |
| --- | --- | --- | --- |
| 内置 Key | 是 | 否 | 仅限私有演示 |
| BYOK | 否 | 是 | 开源、用户自带账号 |
| Serverless 代理 | 否 | 否 | 比赛演示、公开分发 |
| 自建服务器代理 | 否 | 否 | 长期运营、需要备案 |

开发者没有自建服务器，因此选 **Cloudflare Worker**：免运维、免费额度够演示、Secret 不进代码。

### 18.3 Worker 的设计

代理只暴露两个端点：

```text
GET  /v1/models
POST /v1/chat/completions
```

请求链路：

```text
App（Bearer <CLIENT_TOKEN>）
  → Worker：校验令牌 / 白名单 / max_tokens
  → 携带 UPSTREAM_API_KEY 请求千问 MaaS
  → 透传 SSE
```

### 设计取舍

- **不暴露通用转发**：只允许固定上游和两个端点，避免代理被当成免费网关；
- **真实 Key 只进 Secret**：`wrangler.toml` 里只有地址、模型白名单和长度上限；
- **令牌可撤销**：`CLIENT_TOKEN` 泄露时可以单独轮换，不影响上游账号；
- **不做入口限流**：优先保证图片与长回复速度，发现滥用再临时封禁；
- **SSE 直通**：不缓冲完整回复，保留逐字输出体验。

### 18.4 部署与验证

部署命令：

```bash
cd server/cloudflare-worker
npx wrangler secret put UPSTREAM_API_KEY
npx wrangler secret put CLIENT_TOKEN
npx wrangler deploy
```

绑定自定义域名：

```text
https://isle-proxy.ynatech.xyz
```

验证记录：

| 项目 | 结果 |
| --- | --- |
| `GET /v1/models` + 正确令牌 | 200，返回模型列表 |
| 无令牌 / 错误令牌 | 401 `unauthorized` |
| 非白名单模型 | 400 `model not allowed` |
| 非流式对话 | 200，正常正文 |
| 流式对话 | SSE `data:` 逐字返回 |
| 2.1MB 图片请求 | 200，正常返回图片描述 |
| APK 扫描 `sk-ws-` | 0 处 |
| APK 代理地址 | 存在 `isle-proxy.ynatech.xyz` |
| 真机发送消息 | 正常流式回复 |

### 18.5 换 Key 与安全边界

| 变更 | 操作 | 是否重打 APK |
| --- | --- | --- |
| 换上游真实 Key | `wrangler secret put UPSTREAM_API_KEY` | 否 |
| 换代理令牌 | 更新 Secret + `local.properties` | 是 |
| 换代理地址 | 更新 `local.properties` | 是 |
| 换模型 | 更新白名单与 `AI_MODEL` | 是 |

必须承认的边界：

- `CLIENT_TOKEN` 仍可能被反编译提取；
- 它能调用代理，但拿不到真实 Key；
- 模型白名单与 `max_tokens` 把滥用成本压到可控范围；
- 发现异常时轮换令牌并重新分发 APK；
- 更高安全等级可以加设备注册、短期 JWT、Play Integrity，但比赛阶段不必过度设计。

这次改造留下的经验是：**安全方案要匹配分发方式**。私有演示可以内置 Key，公开分发就必须把密钥从客户端拿走。

| 7 | 新建 Android 工程，命名「心屿」 | 包名 `com.isle.companion`，仅 Android |

**立项结论**

- **平台**：原生 Kotlin + Jetpack Compose。端侧 ONNX 推理需要直连原生接口，跨平台方案的 FFI 成本更高。
- **架构**：UI（Compose）→ Domain（Prompt/Memory）→ Data（Room/DataStore/DeepSeek）→ 手写 `AppContainer`，不引入 DI 框架。
- **记忆**：对话后由 LLM 抽取事实 → 端侧向量化 → Room BLOB → 本地加权召回，全程不依赖云端向量库。
- **边界**：不含自建服务端；对话内容仅在发送时传输至用户配置的模型服务。

##### 直接封进 APK 的现实
APK 是公开可解包的，把 Key 写进 `BuildConfig`、`strings.xml` 或 assets，用 jadx/apktool 或直接 `strings` 就能在几十秒内提取出来。R8 混淆、字符串加密、塞进 native 库只能提高门槛，**挡不住有心人**。

后果：Key 泄露后别人可以用来消耗你的额度/余额（真金白银），也可能违反服务商条款；提交物里还可能出现"硬编码密钥"的负面评价。

#### 🤖 AI　`10-15 16:47`

你这个直觉很合理，但**大模型 API 是无状态的**——这就是必须每次重发的原因。

##### 关键机制
`chat/completions` 这类接口，两次请求之间模型**什么都不记得**。它本质是一个函数：`提示词进 → 文字出`。

所谓的"记忆"，**并不存在于模型里**，而是存在**你手机的数据库里**。所以每轮对话前，我们必须把下面这些一起塞进提示词发过去：

```
角色卡（小屿是谁）
+ 我的资料（小彤是谁）
+ 检索出来的相关记忆
+ 最近 12 条对话
```

这不是我们的设计选择，是**所有聊天类大模型的通用做法**（包括 ChatGPT、Claude）。所谓 RAG / 知识库，本质就是"每次检索出相关片段，再喂给模型"。

##### 一个类比
模型像一个**绝顶聪明、但每次说话都会失忆**的人。
你每次开口前，都得先递给 TA 一张小纸条：「这是小彤，她慢热但重感情，上次她说在准备项目」。

递纸条这件事看起来"重复"，但**正是它让 TA 表现得像记得你**。

##### 那"发一次就永久记得"能做到吗？
能，但那是另一种架构：
| 方案 | 谁保存状态 | 说明 |
|---|---|---|
| 现在我们这样 | 你的手机 | 每轮重发上下文（标准做法） |
| 服务端会话/助手 API | 模型厂商 | 由厂商托管上下文，但仍会在后台重新喂给模型 |
| 微调模型 | 厂商 | 把知识"烧"进权重，成本高、更新慢，不适合个人资料 |

DeepSeek 提供的是标准 `chat/completions`，没有会话托管；而且**个人资料随时会改**，塞进权重也不现实。

##### 成本其实不用担心
- 资料那段只有几十个 token，一轮请求里系统提示词整体也就几百 token
- DeepSeek 有**上下文前缀缓存**机制，重复的 system 前缀通常会被缓存命中，费用进一步降低（具体以官方计费文档为准）

所以：**"每轮都发" ≠ 浪费，而是"每次让 TA 想起你"的唯一方式**。真正省 token 的优化方向是——把长历史压成摘要，只留最相关的记忆（我们已经在这么做了）。
